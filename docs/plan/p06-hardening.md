# P06 · 系统可靠性、安全、资源与可访问性

实施依据：2026-10-23 计划；阶段状态统一见 [路线图](ROADMAP.md)。本阶段实现真实 Android 系统入口，采用 JVM、Compose、宿主 Rust、静态检查和 APK 构建验收，不安排设备运行、耗电、24 小时运行或人工 TalkBack 验收。

## 1. 输入、范围与顺序

**开始条件**：P03 已交付异步持久化仓库和独立的连接目标；P04 已交付有界日志与观测；P05 已交付完整策略解析和 Service 接线。仓库读取失败、未知运行结果、策略冲突都必须有可消费的类型，不能用空配置或 false 代替。

按 P06-01 至 P06-08 顺序执行。保留单进程、单 Application 仓库、单 Service 会话拥有者；本阶段不引入独立进程，不升级固定核心。测试替身仅用于 test，main 必须调用真实系统和真实核心。

| 修改位置 | 职责 |
|---|---|
| app/src/main/AndroidManifest.xml、res/values、res/values-v29 | 系统组件、权限、Always-on 支持声明 |
| lib/vpn | 系统启动分类、恢复策略、重试、代次与资源关闭 |
| features/settings、根装配 | 系统设置入口、通知及 Tile 的统一动作接线 |
| lib/profile | 已保存连接目标读取与失效结果；不存运行句柄 |
| app/src/test、app/native/tests | 系统适配器契约、状态/时间/失败序列及资源断言 |

下文 `lib`、`features` 和根 Kotlin 文件相对 `app/src/main/java/com/github/zzwtsy/chuanmen`；资源相对 `app/src/main/res`，JVM 测试镜像生产包。每项只改列出的职责及直接消费方；工程报告填写实际新增文件名。

## 2. 分任务

### P06-01 · 完成通知、Tile 与 Always-on

**修改位置**：`lib/vpn/NativeVpnService.kt`、`VpnSessionCoordinator.kt`、`VpnSessionClient.kt`；新增同包 TileService；`features/settings` 与根动作装配；Manifest 和 values/values-v29 资源。

**开始条件**：P05-06 的平台策略与自动重连配置已完成，仓库能返回 Loading、Ready、ReadFailed。

1. 为 VpnService 的 SUPPORTS_ALWAYS_ON 元数据引用布尔资源：资源名固定为 `supports_always_on`，默认 values 为 false，values-v29 为 true。API 24–28 不启用；API 29+ 接入 isAlwaysOn/isLockdownEnabled。保持 directBootAware=false，不从设备保护存储复制秘密。
2. 系统启动与用户连接通过同一 Service 协调器执行。API 29+ 的无用户命令启动先读取系统 Always-on 状态；仅 Always-on 为真且仓库 Ready 时允许恢复最后一次明确连接目标的最新已保存修订。普通 App 启动、最后查看配置、未保存草稿都不能触发恢复。仓库 Loading 时只注册一个等待任务；Ready 后重新核对当前系统状态和目标，ReadFailed 则结束等待。重复启动事件不得创建多份等待任务。
3. 目标不存在、仓库读取失败、用户尚未解锁或策略无法生成时停止本次连接尝试，显示可操作错误，不选择列表第一项，不后台反复重试解密。用户重试读取成功后或下一次明确系统启动事件才重新评估；本应用不自行调度失败恢复循环。
4. Always-on 开启时，通知、Tile 和 App 的“关闭始终开启”动作打开系统 VPN 设置。用户在系统关闭后，才能按普通断开流程清除恢复意图；不能发送停止后又被本应用自动重启的循环命令。系统关闭 Always-on 后不自动断开，重新读取状态并恢复普通“断开”动作，由用户明确执行。
5. 普通模式的通知与 Tile 调用既有连接/停止动作，不自行维护会话状态。通知显示实际运行配置和状态；重复状态更新不重复响铃；未获 VPN 授权时先进入授权入口。无活动会话时，Tile/通知连接动作只打开 App 让用户选择并确认目标；不得凭最后查看 ID 在后台启动。
6. 系统设置无法解析时显示错误和手动路径，不能崩溃。设置页标明 API 支持范围；不承诺系统永不终止服务。

**失败处理**：前台服务启动被系统拒绝时返回 ForegroundStartDenied，取消本次等待与连接，不后台循环重试；配置加载或目标写入失败时禁止发送引擎 Start。lockdown 下 bypass 或排除应用策略返回 LockdownConflict，保留草稿，不静默改为 all。

**完成断言**：在固定 JVM runtime 中向系统适配器注入 API 24、28、29、37 并验证分支，另静态检查资源版本选择；不为这些测试下载四套设备系统。覆盖 Always-on true/false、lockdown true/false、无目标、读取失败、查看 B 而恢复 A、A 有未保存草稿、目标已删除。断言每个事件最多产生一个启动命令，所有入口共享同一个协调器。构建产物静态核对 Manifest 元数据引用。系统是否实际拉起服务仍未验证。

### P06-02 · 实现有限自动重连

**修改位置**：`lib/vpn/VpnSessionCoordinator.kt` 的 desired/networkChanged 路径、Runtime 的重试状态、Service 的底层 Network 事件适配及对应虚拟时间测试。

**开始条件**：P06-01 已区分用户启动、系统 Always-on 启动与普通启动。

1. 在 lib/vpn 定义重试状态，包含目标 ID、会话代次、尝试次数、下一次时间；使用可注入单调时钟。失败后的等待依次为 1、2、4、8、16 秒，最多 5 次重试，耗尽后保持 RetryExhausted；用户重新点连接或底层 Network 身份发生实际变化才重置一轮预算，重复 onCapabilitiesChanged 不重置。初始明确连接不计入这 5 次重试。
2. 无可用底层网络时挂起重试，不消耗次数。网络恢复同一身份时以尚未消耗的下一次延迟重新计时；切换为不同 Network 身份时开启新预算并在 1 秒后安排一次尝试，重复回调合并。连续连接 60 秒后清零重试次数；短暂成功后再次失败继续原预算。
3. 显式停止、授权撤销、关闭自动重连、切换连接目标和销毁 Service 的控制作用域立即取消旧定时任务；旧回调不能恢复旧配置。修改当前查看网络不影响目标。
4. 格式错误、密钥失效、未授权、无可用配置属于不可重试错误；网络中断和可恢复连接失败才消耗重试预算。错误分类集中定义，不按错误文本匹配。

**失败处理**：UnknownResult 或尚未确认释放旧资源时禁止重试；先走既有查询/停止确认流程。普通模式 autoReconnect=false 时不进入调度；Always-on 的系统启动仍按系统明确意图处理，但应用内部重试也受此开关约束，不假装能阻止系统再次发起启动。

**完成断言**：虚拟时间精确检查五次延迟、预算耗尽、无网络挂起、60 秒清零、停止前后竞态和旧目标回调；每种取消条件之后推进时间均不再发起连接。测试不宣称 Wi-Fi/蜂窝切换实测通过。

### P06-03 · 处理进程重建与授权边界

**修改位置**：`NativeVpnService.kt`、`VpnSessionClient.kt`、`ChuanmenApplication.kt` 和仓库加载状态消费方；对应生命周期模型测试。

**开始条件**：P06-02 的恢复意图与定时任务已分离。

1. 新建进程只从已保存文档恢复配置，不恢复 session ID、TUN fd、处理中状态或草稿。重新查询 Service 实际状态后再更新 UI。
2. onRevoke、onDestroy、启动取消、另一 VPN 接管的事件进入同一串行关闭路径；已关闭资源再次关闭不影响新代次。
3. 用户拒绝授权保留配置和草稿并返回未连接；重新授权必须由新的明确动作触发。禁止自动循环弹授权页。
4. 系统 Always-on 的恢复按 P06-01；普通进程重建不自动连接。force-stop 后的系统行为不由测试模拟结果推断。

**失败处理**：关闭超时保留资源未知状态并禁止复用旧 fd；不得为了恢复 UI 按钮直接清空资源计数。授权拒绝/撤销后所有挂起重试失效，新的明确授权动作才可继续。

**完成断言**：通过重新创建仓库、Application 装配与 Service 测试实例，断言状态重建、失败关闭、重复撤销、启动期间撤销和旧回执丢弃。每条序列检查实际命令和资源拥有者，不只检查 UI 文案。

### P06-04 · 收敛权限、备份和敏感数据

**修改位置**：Manifest、backup_rules.xml、data_extraction_rules.xml、系统 Intent 消费处、P03 加密适配、P05 导入导出错误转换及测试。

**开始条件**：P03 加密存储及 P05 导入导出均已接入正式路径。

1. 核对合并 Manifest：只有系统需要的入口导出；VpnService 使用 BIND_VPN_SERVICE；Tile 使用 android.permission.BIND_QUICK_SETTINGS_TILE；内部动作显式指定组件。外部 Intent 不能直接覆盖连接目标或导入后自动启动。
2. 核对传统备份及 Android 12+ data-extraction 规则：配置密文、密钥关联元数据、日志均不参与系统云备份或设备迁移；用户显式 age 导出不受此规则代替。
3. 密钥失效保留原文件并返回明确错误。导入解析、运行错误、异常对象、日志和诊断导出均不能含秘密；测试使用合成秘密，断言输出不存在该字符串及其常见 JSON 转义形式。
4. 逐条将 Manifest 权限映射到调用 API，删除没有任何生产消费者且不是系统组件必需的权限；权限拒绝有稳定错误入口，不关闭检查绕过失败。

**失败处理**：外部 Intent 多余/缺失参数直接拒绝，不能使用外部提供的组件或嵌套 Intent 继续转发；秘密泄漏测试失败立即阻止任务完成，不能改测试字符串绕过。

**完成断言**：合并 Manifest/备份 XML 静态检查通过，恶意 Intent、缺失字段、错误口令及脱敏回归通过。未进行设备权限交互与 Keystore 硬件行为验收。

### P06-05 · 固定资源边界

**修改位置**：`lib/vpn` 的会话/探测资源拥有者、native session/protector/diagnostics 与日志存储；测试中注入计数器，不增加应用常驻诊断采样器。

**开始条件**：P04 的日志预算和 P05 的所有监听/代理资源已登记所有权。

1. 为每类 TUN fd、外层 socket、探测 socket、任务、回调和 native 句柄记录创建者、关闭者及取消入口；保留一个共享 JNI runtime，不按配置创建 runtime。
2. 用测试注入创建/关闭计数器，覆盖正常停止、启动失败、取消和重复停止；关闭完成后会话拥有的 fd/socket/回调计数为 0；Application 共享 runtime、仍在运行的日志写入器与 Service 生命周期订阅单独列为进程资源，不要求它们归零。不能以 GC 触发作为关闭条件。
3. 验证 P04 日志上限：2000 条内存记录、单文件 2 MiB、最多 5 文件、7 天留存、单条最多 8 KiB；写入前轮转，磁盘失败不阻塞 VPN。首页保留固定 60 秒窗口，页面隐藏后不继续高频 UI 更新。
4. 长序列测试只验证计数器和容器上限，不使用宿主耗时、RSS 或模拟器电池数据宣称手机性能达标。

**失败处理**：任一关闭回执缺失时标为未确认释放，停止后续同资源复用序列；记录资源类型、代次与失败点，不输出裸 fd 之外的敏感网络内容。

**完成断言**：创建失败点逐个注入后无残留会话拥有者，日志容量边界和时钟跳变测试通过。设备 fd、RSS、CPU、温度和耗电未测量；本阶段不据此决定拆进程。

### P06-06 · 完成 Compose 适配与可访问语义

**修改位置**：`features` 的 Screen、共享 components、ui/theme、根 Scaffold 和相应 Compose JVM 测试。

**开始条件**：P03–P05 页面已接正式 UiState。

1. 使用 JVM Compose 测试覆盖 320 dp 与 600 dp 可用宽度、默认与 200% 字体、深浅色；需要滚动时保持主要动作可达，不通过缩小系统字体适配。
2. 校验表单错误与标签关联、图标按钮语义、焦点顺序、连接状态文字、复制成功反馈；颜色不是唯一状态标识。
3. 检查 IME、系统栏 inset 和底部操作区的布局传递；使用约束与语义断言，不能仅更新截图基线关闭失败。
4. 动态色不可用时使用固定主题回退；动效遵循系统缩放配置，不改变会话状态。

**失败处理**：布局断言失败先检查实际约束与 inset 传递；不缩字体、不隐藏主要动作、不删除语义断言。

**完成断言**：2 种宽度 × 2 种字体 × 2 种主题共 8 个组合中，保存、取消、停止和错误入口可访问；IME inset 注入 0/240 dp 时底部操作区均位于可用区域。上述尺寸/字体组合中必需操作存在且可触达，错误能通过语义树定位。JVM 结果不标记为真实系统栏、键盘或 TalkBack 已验收。

### P06-07 · 执行状态组合回归

**修改位置**：现有 test 的协调器、平台策略与状态序列测试，以及 app/native/tests；不新建 androidTest 运行任务。

**开始条件**：P06-01 至 P06-06 的单项回归通过。

1. 按 all/allowlist/denylist、system/custom DNS、IPv6 block/bypass/tunnel 构造 3×2×3=18 个基础组合，再分别设置 lockdown=false/true，共 36 个组合。为 allowlist/denylist 使用一个可见已安装包，为 tunnel 提供当前代次 IPv6 地址；普通组合逐一断言 Builder 参数，lockdown+bypass 或 lockdown+非 all 名单按 P06-01 返回 LockdownConflict。另覆盖空 allowlist、失效包、无 DNS、缺 IPv6 地址与 MTU<1280 五类非法输入，均在建立 TUN 前拒绝。
2. 为普通与 Always-on 两种启动来源分别执行：连接 → 保存新修订 → 应用失败 → 显式恢复 → 停止；Always-on 序列的停止先模拟用户在系统设置关闭 Always-on，再发普通停止命令，不能与 P06-01 的规则矛盾。检查 saved/applied 分离、元数据保留及最终资源计数。
3. 在虚拟时间下循环 100 次启动/取消/停止序列；每轮断言代次递增、旧回执被丢弃、关闭后无重试任务。循环失败必须定位首个失败序列，不增加重试次数掩盖。
4. 执行 [工程阶段检查组合](../development/setup.md#工程阶段检查组合)，编译 androidTest，不连接设备。

**失败处理**：第一个失败用例保留确定性输入、虚拟时刻和回执顺序；修复后重跑受影响序列，不能将失败组合从矩阵删除。

**完成断言**：全部确定性序列与工程检查通过；报告标记“宿主/模型序列”，不能称为 24 小时运行或系统后台可靠性实测。

P06-01 至 P06-08 均达到各自完成断言，所有阻塞缺陷修复，并保存对应源码与检查定位后结束。本阶段不执行 24 小时/第二 OEM 运行、网络切换、release 冒烟、16 KB runtime、耗电或人工可访问性验收；这些取消项目不作为未完成待办反复排入计划。
