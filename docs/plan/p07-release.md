# P07 · Beta 验证、发布准备与维护交接

> 状态：待实施。预计工程工作 1–2 周。账号审核、商店要求的测试周期和外部审核不受本估算保证，必须提前确认。

## 1. 目标

形成可追溯、可安装、可升级、可报告问题的 Beta 版本。
将前六阶段的能力与限制如实呈现，并为后续核心升级留下明确路径。
准备完成后再执行有权限的分发或上架动作，不能把文档准备等同已发布。

## 2. 前置门槛

- P06 的同一候选构建达到质量门槛，阻塞缺陷已关闭。
- P05 能力矩阵、兼容说明和未完成能力与实际产品一致。
- 已确定首发渠道、应用 ID、签名策略和维护者职责。
- 生产签名、发布 token 与账号权限由适当负责人管理，不交给文档或原型。
- 当前 Google Play、目标 SDK、原生库兼容与隐私要求已再次核对。
- 渠道需要的账号验证、测试资格与审核周期已经进入排期。

## 3. 分任务

### P07-01 · 冻结可发布候选

1. 固定 App、核心、bridge、配置 schema 和依赖版本。
2. 标记本候选实际包含的 ABI、最低系统版本与能力集合。
3. 生成可重现的 release 构建，确认关闭 demo、测试服务和调试菜单。
4. 保存签名前与签名后产物的来源记录，避免无法解释的二次打包。
5. 对最终 APK / AAB 计算 SHA-256，与源代码 tag 和构建记录对应。
6. 不在发布冻结期间顺手升级 AGP、Rust、Compose 或核心。
7. 任何二进制或关键配置改变都生成新候选，并复验受影响门槛。

### P07-02 · 验证安装、升级与恢复

1. 在支持系统与 ABI 上安装最终候选，不能只验证 debug。
2. 从上一 Beta / 测试 schema 升级，保留本地名称、配置和 Android 策略。
3. 对运行中升级、升级后首次启动和未解锁相关状态验证真实行为。
4. 验证签名不匹配时错误清晰，发布渠道不能意外互相破坏升级路径。
5. 对卸载后恢复、加密密钥缺失和错误备份密码给明确说明。
6. 发布回退以兼容版本或前向修复实现，不假设系统允许任意降级安装。
7. 数据 schema 不兼容时保留备份与迁移计划，不能指导用户直接清数据。
8. 再次确认应用启动不自动连接错误配置或把过期状态当作运行。

### P07-03 · 完成分发与供应链材料

1. 按渠道输出正确产物：APK 用于直接安装，AAB 用于对应商店流程。
2. 记录签名证书指纹、校验和、源代码链接及可核对的核心版本。
3. 检查最终原生库的 ABI、加载和当前要求的页面大小兼容。
4. 汇总许可证、第三方声明、上游源码与必要的修改说明。
5. 生成依赖清单 / SBOM，记录构建来源和已知风险处置。
6. 把崩溃符号与 mapping 按版本受控保存，不能把秘密混入公开产物。
7. 发布说明中的“已支持”从能力矩阵生成，不从配置表单数量推导。
8. 若采用两个渠道，明确签名、更新来源与包名策略，避免用户无法升级。

### P07-04 · 准备用户资料

1. 写首次启动指南：创建 / 导入配置、系统授权、连接、看流量和断开。
2. 解释本地配置名、核心网络名与本设备名的区别。
3. 解释保存 / 待应用 / 运行状态，不让用户以为保存就是连上了。
4. 用真实 release 截图展示产品，演示截图必须明确为示例数据。
5. FAQ 覆盖无设备、无流量、复制、DNS、应用分流、IPv6 和系统后台限制。
6. 明确日志包含的范围、如何脱敏导出、哪些信息不需要公开提交。
7. 说明高级服务的适用条件，尤其 Portal、出口与子网代理。
8. 不宣称流量动了就证明所有配置生效，也不承诺所有机型不断线。

### P07-05 · 制定并执行 Beta 验证

1. 招募覆盖系统版本、OEM、网络类型和高级用例的测试者。
2. 每人使用独立测试网络或自己的已授权网络，不共享生产秘密。
3. 给任务清单：创建命名、连接、复制、编辑保存、应用、切网、查日志和导入。
4. 测试反馈记录版本、设备、时间、最小步骤和脱敏日志。
5. 使用稳定问题分类：崩溃、连接、配置、数据显示、系统兼容和 UX。
6. 不默认上传诊断；如引入遥测需先确定必要性、告知与选择机制。
7. 每日归并同因问题，优先关闭数据丢失、秘密泄漏和无法断开等阻塞。
8. 达到退出标准后再扩大测试范围，不以安装人数替代任务通过证据。

### P07-06 · 完成发布复核与执行包

1. 核对当前商店的 VPN 声明、目标系统、前台服务与数据处理要求。
2. 权限与数据安全声明必须对应真实代码、日志和依赖，不能复制通用模板。
3. 对加密关闭等选项及传输行为做渠道要求复核，有冲突时记录版本策略。
4. 准备版本号、更新日志、产物、截图、许可证和兼容说明。
5. 制作一份可审阅的发布清单，明确将向何渠道、何用户发布什么版本。
6. 所有可逆的打包与检查先完成，最后由具备权限者执行正式分发。
7. 发布后核对下载文件哈希、版本和安装结果，防止上传错包。
8. 若外部审核阻塞，保留候选和原因，不宣称已经上架。

### P07-07 · 建立维护和核心升级流程

1. 核心升级由精确版本差异、字段变化和桥兼容核对开始。
2. 自动化发现变化可以辅助提示，不能自动合入未知 ABI 或配置语义。
3. 每次升级重跑 fd / protect / 生命周期、codec 和关键高级服务用例。
4. 保存上一可用版本与兼容备份方案，明确哪些回退会遇到 schema 限制。
5. 固定已验证的升级与诊断步骤后，再创建对应项目 skill。
6. skill 只引用真实命令与 fixture，不复制整份架构文档。
7. 建立支持版本、已知问题、响应负责人和下一次兼容复核日期。
8. 将 Beta 暴露的共性问题补入测试 / 文档，避免只写聊天记录。

### P07-08 · 完成交接与下一轮排期

1. 按 P00–P07 核对交付物、证据和未完成条目。
2. 把已验证事实、条件支持和待研究项分别列出，不混成“全部完成”。
3. 为下一轮候选建立独立 backlog，避免发布前临时加功能。
4. 按真实工时和阻塞原因修正以后估算，区分工程时间与平台等待。
5. 检查根 AGENTS、局部规则、命令、ADR、skill 和代码保持一致。
6. 一名未参与主线开发的协作者完成一次从 checkout 到 demo / 测试的演练。
7. 指定谁维护核心、谁维护发布、谁处理用户问题，避免知识只在 AI 会话中。

## 5. 依赖与并行边界

- 用户资料、许可证整理、渠道准备可在 P06 后半并行。
- 最终 release 安装与升级测试依赖最终签名候选，不能用旧 debug 结果替代。
- 发布二进制由单一负责人生成和校验，其他人只读复核产物。
- 准备材料与正式分发分开，未获发布授权时可以完成可审阅执行包。
- 平台审核等待不应推动团队未经评审更改隐私或权限模型。

## 6. 验证与明确通过标准

| 项目 | 通过标准 |
|---|---|
| 候选追溯 | 源码、核心、依赖、schema、ABI、签名与 SHA-256 完整对应 |
| 真正 release | 最终分发文件能在约定矩阵安装和启动，无 demo 数据或测试秘密 |
| 升级 | 受支持升级路径保留配置、本地名称和安全策略，无静默数据丢失 |
| 用户任务 | Beta 清单关键任务均有真实执行证据，不能仅记录“看起来正常” |
| 阻塞问题 | 数据丢失、秘密泄漏、错误自动连接、无法停止等阻塞为 0 |
| 文档一致 | 支持声明、权限说明、配置范围和真实构建一致 |
| 发布校验 | 产物、下载地址与哈希一致；有权维护者完成发布记录 |
| 维护交接 | 干净环境演练成功，升级 / 诊断流程可由第二人执行 |

建议 Beta 至少覆盖 5 种设备 / 系统组合和 3 类网络条件；这是项目采样建议。
它不替代分发平台针对账号、测试者或测试时长的具体规定。
若暂未分发，只能称“发布准备完成”，不能称“Beta 已发布”。

## 7. 失败回退与本阶段不做

- 最终候选存在阻塞缺陷则暂停扩大分发，回到相关阶段修复并生成新版本。
- 渠道审查问题保留明确原因，不通过隐藏功能或虚假声明绕过审核。
- 发现签名或密钥泄漏按既定应急处理，不把新密钥随手提交仓库。
- 不在发布阶段新增账号、云日志、付款或自动更新体系。
- 不未经说明切换核心版本来处理单一发布问题。
- 外部测试 / 审核周期超出估算时调整排程，不压缩数据迁移与真机验收。
