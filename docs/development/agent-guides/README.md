# 代理指南的维护方式

## 本目录是什么

本目录提供未来原生工程的局部指令样板和维护约定。`*.example.md` 是设计素材，不是当前活动的 `AGENTS.md`，也不证明对应 Android 模块已经实现。只在实际模块已存在，且 P01/P02 已确认其职责、公开入口与验证命令后，才把需要的局部内容整理到那个模块的 `AGENTS.md`。

根入口是 [项目 AGENTS.md](../../../AGENTS.md)。总体工程原则见 [AI 友好 Android 工程](../ai-friendly-android.md)。

## 1. 文件名使用 AGENTS.md

本项目采用复数 `AGENTS.md`。开放格式使用普通 Markdown，没有强制 schema；无需同时维护 `AGENT.md`、`CLAUDE.md`、`.cursorrules` 等多份互相漂移的完整副本。某个工具需要其他入口时，用小型适配说明引用规范来源，并在该工具中验证加载效果。[AGENTS.md 官方说明](https://agents.md/)。

## 2. 区分开放约定与宿主实现

下述 Codex 行为以 2026-10-11 检索的文档为依据，来源见 [研究索引](../../research/sources-agents.json)。

| 范围 | 可确认的内容 | 对本项目的操作要求 |
|---|---|---|
| 开放 AGENTS.md 约定 | 根文件提供项目说明；可用局部文件细化子项目；文件是 Markdown | 把它当可移植内容，不把所有工具的搜索行为当成统一规范 |
| Codex 实现文档 | 启动时沿项目根到当前工作目录收集指导；每目录最多一份；检查 override、常规文件及配置的 fallback | 要在子模块工作时确认其规则已加载，或显式阅读对应文件；不能假定根目录启动就自动加载所有后代 |
| 其他代理/IDE | 是否支持、入口名称、继承和缓存规则可能不同 | 只适配实际使用的工具；根据其当前文档做一次加载验证 |

在上述文档版本中，Codex 的同目录 `AGENTS.override.md` 优先于常规文件，默认合并字节限制由宿主配置控制。因此本项目不通过复制大文档或改个人全局配置解决“上下文不够”，而是缩短根入口并按任务链接细节。[Codex AGENTS.md 发现与优先级](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

## 3. 什么时候需要局部规则

只有模块存在根文件不能清楚表达的独特边界时再添加：

- `:core-bridge` / `native/` 有线程、句柄、文件描述符和核心版本兼容约束。
- `:app` 有特定预览、语义与主题验证入口，且路径已经稳定。
- 构建目录有实际约定插件、升级顺序和专用验证。

单纯“使用 Kotlin”“遵守命名习惯”“别引入 bug”不是建立一个局部文件的理由。每个局部文件说明自身作用范围、公开入口、特例和相关验证，不重复根文件的不变量、授权范围或整个设计文档。

可参考的样板：

- [Android UI 局部说明](android-ui.example.md)
- [Native 桥接局部说明](native-bridge.example.md)

## 4. 局部指令的验证

P01 为每个实际使用的代理记录一次加载检查：工具与版本、启动目录、报告的指导文件及实际适用范围。检查过程只要求代理列出加载来源和概括约束，不让它修改业务代码。不默认改变其审批策略，也不复制官方示例中的权限参数。

之后用一个很小的任务验证内容是否可执行：从根导航找到模块、运行文档中的相关命令、说明输出和未覆盖范围。若文件内命令不存在或模块路径改名，修正文档；不要让代理每次临场猜正确任务名。

## 5. 更新规则

| 变化 | 同步修改 |
|---|---|
| 模块移动或职责变化 | 任务导航、模块说明及局部指令 |
| Gradle variant / task 变化 | 脚本、可用命令、CI，最后再更新指令中的引用 |
| 新发现一个反复发生的危险误用 | 先判断能否由类型或测试禁止；不能机械验证时加入简明局部规则 |
| 根与局部重复 | 保留唯一权威位置，其余改链接 |
| 临时探索未采用 | 不放入永久指令；结果记到阶段证据或决策记录 |

一个规则有成本：它会占用每次相关任务的上下文。只有能减少真实误解、重复查找或错误行为的说明才值得常驻。技能的按需工作流与评估方法见 [Agent Skills 策略](../agent-skills-strategy.md)；依据：[技能创建最佳实践](https://agentskills.io/skill-creation/best-practices)。
