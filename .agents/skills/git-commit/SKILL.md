# Git 提交编写

让未来维护者只看提交信息就能理解改动的目的、结果和必要取舍；让实际提交内容与这份说明一致。

## 确定任务边界

- “写 commit 信息”“看看怎么提交”“审查 message”：只读检查，给出文案或拆分方案，不改暂存区、不创建提交。
- “提交 git”“按这个方案提交”：在授权范围内执行本地提交。沿用会话中的已有授权，不要求重复确认。
- 推送、标签、发布、amend、rebase、reset、stash 不从本地提交授权推导；调用本技能本身也不等于授权提交。
- 只有文本或补丁时，根据给定材料起草并注明证据范围；不要虚构仓库约定、动机、测试结果或 issue 编号。

## 从实际差异确定内容

先查看适用的 AGENTS.md、贡献指南、提交模板及已有 lint/hook 规则，再参考近期非合并提交及受影响路径的历史。用户当前要求优先；历史样例用于补全约定，不能覆盖明确规则。只读检查例如：

```sh
git status --short --branch
git diff --stat
git diff --cached --stat
git diff
git diff --cached
git ls-files --others --exclude-standard
git log -10 --no-merges --format=%s
```

按任务范围缩小 diff；统计不能代替补丁。`git diff` 不展示未跟踪文件，准备纳入的文件需单独检查。读取周边代码只为核对本次行为和契约，不扩展成全仓审查。

区分工作区、暂存区和目标提交。用户指定“已暂存”时以暂存区为准；全部差异不能直接当作待提交内容。遇到冲突或进行中的 merge/rebase/cherry-pick，先辨明当前操作及授权，不用普通提交流程顺手完成它。

## 划分逻辑提交

一个提交表达一个完整意图，以能独立理解、验证和回退为判断标准，不按文件数、目录或行数机械拆分。

- 同一行为所需的实现、回归测试、契约文档和必要依赖更新通常放在一起。
- 无关修复、广泛格式化、纯移动或重命名与行为改动，能独立成立时拆开。
- 不为拆分制造无法编译、缺少迁移或测试与实现错位的中间状态；有依赖时按依赖顺序排列。
- 多个提交给出每组目的、路径或 hunk 边界及顺序；小改动直接起草，不强制凑多组。

## 编写信息

### 标题

统一使用 Conventional Commits：`<type>[optional scope][!]: <description>`。description 写“动作 + 对象 + 必要的结果或条件”，例如 `fix(parser): 拒绝缺少端口的节点地址`。避免只有“优化代码”“修复问题”“update”或文件清单。

语言按用户要求及仓库约定选择；无约定时跟随用户语言。英文使用祈使式，如 `fix`、`add`；中文直接用“修复”“添加”“限制”，不写“我修改了”。通常不加句末句号。

标题约 50 字符、正文约 72 列是可读性建议，不是 Git 或 Conventional Commits 的通用硬限制。中文不机械套用英文字符宽度；已有 commitlint 限制按实际配置执行，不为了压长度省略关键语义。

### 正文与尾注

标题足以解释的小改动可以没有正文。其余提交在标题后空一行，用自然段说明：什么条件下存在什么问题、改动后如何表现、为什么采用这个方案。仅保留影响理解的取舍、兼容性和迁移信息，不复述 diff 或聊天过程。

正文应脱离当前会话也能读懂；issue 链接补充上下文，不能替代问题说明。有测试代码不等于测试通过，工作区测试通过不自动证明每个拆分提交通过。按项目需要记录实际验证及边界，不强制每条信息添加 `Tests:` 模板。

`Refs:`、`Fixes:`、`Closes:` 等只引用真实事项；仅在确实解决且符合托管平台约定时使用关闭语义。`Signed-off-by` 是项目认证约定，不等于密码学签名；不伪造签署、审查、共同作者或代理身份。AI 编码代理按下文署名规则处理。

### AI 编码代理署名

- 仅当当前代理对本次提交快照中的代码有实质性生成或修改贡献，且有效的会话、工作区及仓库策略允许时，添加 AI 代理署名；仅讨论、审查或建议不作为共同作者依据。
- `Co-authored-by` 记录代理工具的已配置身份，不用底层模型名称代替。需要模型溯源时，且仓库约定允许，用 `Assisted-by: <工具> (model: <供应方>/<模型>)`；模型名称不伪装成 Git 用户，也不推测邮箱。
- **Codex**：有效的 Codex 工作区署名策略启用时，添加且仅添加 `Co-authored-by: Codex <noreply@openai.com>`；策略关闭时不加。遵守当前工作区或组织策略，不用 skill 覆盖明确关闭的状态。
- **Claude Code**：使用工具当前有效的 commit `attribution` 配置值，不用底层模型名称替代工具署名。旧的 `includeCoAuthoredBy` 配置已弃用；没有有效署名值时，不猜邮箱或创造身份。
- **Pi**：Pi 上游没有统一的官方 `Co-authored-by` 身份。只有仓库或用户提供了确定的 GitHub 账号身份和邮箱时才使用该 trailer；只需记录工具或模型参与时，按仓库约定使用 `Assisted-by`。
- 保留已有署名和其他真实 trailer；精确重复的署名只保留一条。新 trailer 放在提交正文后，并与正文之间留一个空行。

### Conventional Commits

起草、审查和执行提交统一采用 Conventional Commits 1.0.0。历史中的无前缀标题不作为省略类型的依据；在该格式内遵守仓库明确的类型、scope 和 lint 约束，不自动安装工具或改写已有提交。

```text
<type>[optional scope][!]: <description>

[optional body]

[optional footer(s)]
```

type 使用小写英文；scope 可选，取稳定的业务或模块名称，不为每个文件新造 scope。description 和正文按用户语言及仓库约定书写，可以使用中文。

| type | 适用改动 |
| --- | --- |
| feat | 新增功能 |
| fix | 修复缺陷 |
| docs | 仅文档变化 |
| refactor | 不改变外部行为的代码重构 |
| perf | 有证据支持的性能改进 |
| test | 测试或测试辅助代码 |
| build | 构建系统或依赖管理 |
| ci | CI 配置与自动化 |
| style | 不影响代码含义的格式变化，不用于 UI 功能变化 |
| chore | 不适合上述类型的维护工作 |
| revert | 撤销已有提交，正文说明被撤销提交及原因 |

上述是本 skill 的常用类型约定，额外类型并非规范强制集合；仓库有明确集合时遵守其配置。按提交的主要意图选一种类型；无关改动优先拆分，不用 chore 掩盖功能或缺陷修复。

破坏兼容的改动必须用 `!` 或 `BREAKING CHANGE:` 标识，并说明具体影响和迁移方式；不限于 `feat`。规范允许仅使用 `!`，但提交描述必须交代破坏性变化，复杂迁移优先放正文或尾注。不要用 `refactor` 掩盖行为变化，或在没有测量时写性能提升数字。

需要核查规范、查找示例或处理 breaking change、签署、squash 文案时，读取 [references/best-practices.md](references/best-practices.md)。

## 执行已授权的本地提交

提交前重新核对目标 diff、暂存区及授权范围，并完成项目要求且适用于本次变更的检查。保留用户的部分暂存选择和无关变更；不要默认使用 `git add -A`、`git add .` 或 `git commit -a`。

| 当前情况 | 处理方式 |
| --- | --- |
| 暂存区恰好等于本次目标 | 审查 `git diff --cached`，普通 `git commit -F` 提交该快照，不附带路径 |
| 目标文件尚未暂存，暂存区无无关内容 | 仅暂存目标路径或 hunk，复查暂存区，再普通提交 |
| 暂存区有无关文件，但目标文件的全部工作区改动均获授权 | 可用 `git commit --only -F <message-file> -- <明确路径>`；先以 `git diff HEAD -- <明确路径>` 审查完整内容，提交后核对无关暂存内容未变 |
| 同一目标文件同时有需提交及需保留的改动 | 保留 hunk 边界；已有暂存快照准确且无无关暂存内容时普通提交，否则先确定能保留原暂存内容的隔离方案；边界不明时只询问具体内容范围 |

**`--only` 并非“只提交这些文件的已暂存部分”。** 它采用指定路径的工作区内容，带路径的普通 `git commit` 也默认如此。`MM`、`AM` 提示部分暂存风险；不检查同一文件的两份 diff，就不能用整文件 `add` 或带路径提交代替 hunk 提交。

用工具的结构化写文件能力，或正确引用的 heredoc，将完整信息写入仓库外的临时 UTF-8 文件，再传给 `git commit -F`。保持真实换行；不要把文案中的反引号、`$()` 或 `\n` 直接拼入可执行 shell 字符串。文件名也需正确引用，并在路径前使用 `--`。

保留 hooks 和既有签名要求。失败时检查输出和当前状态：若 hook 修改了文件，重新审查并按需验证；不要默认 `--no-verify`、关闭签名、反复重试或擅自改身份。权限或配置阻塞如实报告，不能靠更改无关 Git 状态绕过。

成功后检查 `git log -1 --format=%B`、`git show --stat --oneline HEAD`、相关提交补丁和 `git status --short`，确认实际内容、信息和剩余暂存/未暂存状态符合预期。不要顺手清空剩余修改或推送。

## 交付

- 只写信息：给一份可复制的推荐文案；必要时简述依据或未验证之处。
- 拆分方案：给提交顺序、每组边界及推荐信息，说明依赖。
- 审查信息：指出具体不准确或不合约定处，并给修订稿。
- 已执行：报告实际 commit hash、标题、验证结果和保留的改动；失败时区分已创建与未创建的提交。
